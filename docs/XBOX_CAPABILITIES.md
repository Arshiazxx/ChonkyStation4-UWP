# Xbox Capability Probe

## Milestone

**M5 — Xbox Capability Probe**

Authoritative emulator baseline: `liuk7071/ChonkyStation4` at `310269290a3c256f5911d4bc7e441489bffffbf6`.

Milestone status: **PARTIAL**.

The probe implementation and repository-side validation are complete. The available execution environment does not contain the Windows/UWP MSBuild toolchain and is not Xbox hardware, so the project could not be compiled, packaged, or run here. Consequently this document does **not** claim any Xbox capability as measured `SUPPORTED` or `UNSUPPORTED`.

## Purpose

`platform/xbox/XboxCapabilityProbe` is a dedicated UWP diagnostic application. It measures the host facilities that later milestones need instead of assuming that desktop Win32 behavior is available in Xbox Dev Mode.

Its runtime output is `xbox-capabilities.json` in the application's `ApplicationData::Current->LocalFolder`.

The repository-root `xbox-capabilities.json` is deliberately a **NOT_RUN baseline**. It contains no fabricated `SUPPORTED` results and is intended to be replaced or archived alongside output captured from a real Xbox Dev Mode run.

## Classification rules

Each result has both:

- `observed`: what happened during the current process (`PASS`, `FAIL`, or `NOT_TESTED`), and
- `status`: the Xbox compatibility classification.

Allowed compatibility classifications are:

| Classification | Meaning |
|---|---|
| `SUPPORTED` | The probe was actually running on `Windows.Xbox` and the operation succeeded. |
| `UNSUPPORTED` | The probe was actually running on `Windows.Xbox` and the operation failed. |
| `UNKNOWN` | The probe cannot make a meaningful determination. |
| `REQUIRES_HARDWARE_TEST` | No authoritative Xbox run has established the result. A desktop/UWP observation is not promoted to an Xbox claim. |

The implementation determines Xbox execution from `AnalyticsInfo::VersionInfo->DeviceFamily == "Windows.Xbox"`.

## Probe coverage

### Memory

The application measures:

- native system page size;
- allocation granularity;
- current UWP application memory usage and application memory-usage limit;
- bounded address-space reservations at 256 MiB, 512 MiB, 1 GiB, 2 GiB, and 4 GiB;
- a 16 MiB reserve/commit/write/read test.

These bounded allocations are capability sampling only. M6 contains the exact upstream guest-address-space diagnostic.

### Virtual memory

The application measures:

- reserve/release/re-reserve behavior at the same address;
- `PAGE_READONLY` transitions through `VirtualProtectFromApp`;
- `PAGE_EXECUTE_READ` transitions through `VirtualProtectFromApp`;
- restoration to `PAGE_READWRITE`;
- `FlushInstructionCache` availability.

The fixed-address test intentionally uses an address first returned by the OS. It does **not** claim that ChonkyStation4's required guest base address can be reserved; that exact requirement belongs to M6.

### JIT-related gates

M5 measures whether a UWP page can transition from writable to executable/readable using `VirtualAllocFromApp` plus `VirtualProtectFromApp`, and whether the instruction-cache flush API is callable. The probe manifest declares `codeGeneration` for this diagnostic.

It does not request an RWX page, and it explicitly does **not** execute generated bytes. `generated_code_execution` and `guest_tls_abi` remain `REQUIRES_HARDWARE_TEST`. Executing dynamically generated/native guest code is reserved for M7.

### CPU/threading

The probe measures:

- `std::thread::hardware_concurrency()`;
- creation and joining of 32 worker threads;
- `std::mutex` plus `std::condition_variable` synchronization;
- a bounded monotonicity sample of `std::chrono::steady_clock`.

These tests establish basic host threading primitives only. They do not validate ChonkyStation4's pthread-win32/TLS/native-guest ABI assumptions.

### Graphics

The probe attempts:

- DXGI factory creation;
- hardware-adapter enumeration;
- D3D12 device creation;
- highest successfully checked feature level;
- shader model query;
- root-signature version query;
- selected format support (`BGRA8`, `RGBA8`, `RGBA32_FLOAT`, `BC1`, `D32`);
- bounded shader-visible descriptor heap creation;
- bounded committed default-heap buffer allocation.

The probe deliberately avoids WARP/software fallback so a missing hardware D3D12 path is not disguised as target support.

### UWP services

The application measures or exposes:

- local-folder file create/write/read/delete;
- Windows networking API access and active-profile visibility;
- Gamepad API access and currently visible controller count;
- default audio-render endpoint visibility;
- packaged application launch.

Actual external network connectivity is not tested. A physical controller cannot be claimed unless one is visible during the run. Suspend/resume recovery requires a real lifecycle transition and therefore remains a runtime test.
